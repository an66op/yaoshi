## 3. 已确认问题与复现依据

### F1 / P1：五球的sum大小计算不可能正确覆盖大、小

范围：7个SSC/幸运5、3个PC、快乐8六合彩，共11个当前五球0～9彩种。

`sum`结算先取前两球，最大18，却使用五球阈值23。因此正常号码范围内，“大”恒输、“小”恒赢。聊天输入的冠亚和大小可以进入此分支，不只是后台未使用代码。

例：输入`冠亚/大/10`，开奖`[9,8,1,2,3]`。后端用17与23比较，判“大”负；页面反而按阈值12显示“17大单”。完整五球之和为23，但当前sum并没有使用全部五球。最终应采用原版的哪一种和值定义需确认；“大小两边有一边完全不可能命中”本身已是确定问题。

依据：`backend/services/settlement.go:698`、`:789`；`backend/services/bet_admin.go:1636`。

### F2 / P1：五个平台彩仍使用固定关联的号码生成公式

范围：SG时时彩、PC加拿大、加拿大28、加拿大2.0、快乐8六合彩，当前都为`source_kind=platform`。

`defaultDrawNumbers`的五球公式等价于：

```text
s, (s+4)%10, s, (s+8)%10, (s+8)%10
```

第一球恒等于第三球，第四球恒等于第五球；前三恒为对子。对`seed % 10`的10种情况穷举结果相同。结构化接口允许对子等形态，因而会出现某些玩法恒中、其余形态不可能中的问题。不能把这套公式当成覆盖所有组合的正式独立随机开奖。

依据：`backend/services/simulated_draw.go:20`、`:30`；`backend/services/settlement.go:522`、`:961`、`:984`。

### L1 / P1：七球六合彩开奖号码与投注号码域不匹配

范围：香港、新澳门、老澳门、宾果六合彩。当前实际均有7球记录，号码存在大于9的值，但非赛车投注限制仍为前5位、单个0～9。

- 不能表达第6/7球的号码投注。
- 不能表达单个49等两位号码：结构化号码校验拒绝大于9。
- `1/49/100`会拆成第一球4与9各100，而不是单个49号100。
- 未实现专属特别号、生肖、波色等玩法码。原版是否需要哪些玩法及49特殊处理仍须取得规则，不能直接照行业惯例增加。

依据：`backend/services/bet_admin.go:1578`、`:1620`；`backend/services/assistant_bet.go:590`、`:691`。

### L2 / P1：宾果六合彩有“允许投注但不可能命中”的形态

转换函数取7个互异号码；通用校验却允许豹子、对子，结算判断前三球原值是否重复。这个源下豹子、对子不可能命中。普通聊天入口暂不能表达形态，结构化下注接口仍允许，因此不能只靠缺少界面当作安全保护。

依据：`backend/services/lottery_sources_168.go:464`；`backend/services/bet_admin.go:1651`；`backend/services/settlement.go:811`。

### O1 / P1（未开放）：20球被结算器按赛车处理

范围：福彩快乐8、台湾宾果，目前未分类，不是会员已开放彩种。

投注校验按非赛车允许总和尾0～9；结算却只因球数大于等于10就切为赛车精确冠亚和值，并把号码0转换成10。同一玩法的输入契约和结算契约不一致。两个彩种的结果图片还截取前10球，缺后10球。

例：前两球10、20，非赛车尾0可通过号码范围校验，结算却用精确30与0比较。

依据：`backend/services/bet_admin.go:1647`；`backend/services/settlement.go:644`、`:704`；`new/src/utils/drawResultCardCanvas.ts:108`、`:202`。

### F3 / P2：赔率目录的形态示例无法在聊天中使用

目录给出`豹子/50`、`顺子/30`、`对子/20`、`半顺/15`、`杂六/10`，但助手没有这些词的解析分支，返回无法识别。结构化接口支持与聊天入口缺失应分别说明，不能说会员已经有完整九玩法。

依据：`backend/services/play_catalog.go:50`；`backend/services/assistant_bet.go:656`。

### F4 / P2：非赛车开奖结果标签与结算不一致

房间历史栏固定使用赛车第10位反向比较，并固定用12判断冠亚大小。

- 五球`[9,8,1,2,3]`：页面龙虎为“虎虎虎虎虎”，因为比较索引全部不存在；后端与开奖图片前两组均为龙。
- 七球`[12,9,34,25,40,7,2]`：页面首组龙虎显示虎，后端按12与2比较判龙；页面和21标大，后端sum阈值23则判小。
- 开奖图片遇到相等直接显示虎，后端则判和。是否应退本金还需原版规则，不应擅自调整。

依据：`new/src/pages/GameRoom.tsx:126`；`new/src/utils/drawResultCardCanvas.ts:38`；`backend/services/settlement.go:686`、`:789`。

### F5 / 功能缺口：非赛车没有专用详细选号面板

正常入口有明确保护，仅“赛车/飞艇/幸运10”可进入详细板。其他彩种显示“暂未配置详细选号面板”，只能尝试聊天输入。不是非赛车正常入口直接套用十名次面板。

依据：`new/src/pages/GameRoom.tsx:122`、`:860`。

### R1 / P2：超范围冠亚和值变成另外的投注

完整数字不在3～19时，解析器没有直接拒绝，而进入逐字符分支：

- `冠亚/99/20` → 两项和值9各20，合并为和值9金额40。
- `冠亚/34/20` → 和值3与4各20，共40。

默认快捷键盘即可输入；这与本地文档“完整和值3～19作为一个投注项”和代码“多和值用#分段”注释不符。这里尚未拿到原版对组合和值的完整定义，因此结论是本地契约缺陷，不是假定原版语法。

依据：`backend/services/assistant_bet.go:624`、`:761`；`backend/controller/user/member.go:1190`；`docs/规则解析.md:72`。

### R2 / P2：详细板能生成后端必拒绝的长指令

详细板选满允许的171项时，单注20生成387字符；改为100生成418字符。界面仍允许提交，后端却限制400字符。结果是整单拒绝，不是已确认部分成交或重复扣款。

依据：`new/src/components/FullBetBoard.tsx:40`；`new/src/utils/fullBetSelection.ts:43`；`backend/services/assistant_bet.go:509`。

### R3 / P2：金额精度规则在入口间不一致

`1/2/1.234`在助手解析中被静默舍入到1.23，详细板拒绝超过两位小数。本地文档也要求最多两位。关闭内置键盘后的原生输入或命令接口可以触发；默认内置键盘无小数点键。是否应统一为整数金额应另按用户产品要求决定，不能在本轮审查中自行改动。

依据：`backend/services/assistant_bet.go:699`；`new/src/utils/betParser.ts:117`；`new/src/utils/fullBetSelection.ts:25`。

### R4 / P3：赛车开5时，输单备注把“小”写成“大”

投注冠军大、开出5：派彩判输正确，但说明生成“5(大/单)”。判奖阈值为6，通用描述阈值却为5。此项是说明错误，不是已确认派彩错误。

依据：`backend/services/settlement.go:675`、`:772`、`:908`。

### R5 / 兼容接口：省略玩法码时第6名与总和歧义

直接下注接口允许省略`play_code`，`position=6, selection=大`会被推断为冠亚和，而不是第六名大。当前详细板和助手显式提交玩法码，不受影响；不应报告成现有选号板串位。

依据：`backend/controller/user/member.go:408`；`backend/services/play_catalog.go:117`。

## 4. 数据源与原版对照缺口

### D1：宾果系列是本地转换，不是七个独立原版结果源

七个宾果彩种共用台湾宾果原始结果，再按本地函数转换。SSC四种取不同五数字窗口的个位；赛车A/B按起点0/10转换并补齐1～10；六合彩取`原号码%49+1`后去重。代码能运行或测试通过，不证明这就是原版转换公式，必须使用原版同期期号和完整结果逐期交叉核对。

依据：`backend/services/lottery_sources_168.go:60`、`:182`、`:418`、`:431`、`:464`。

### D2：非赛车源校验和时间处理仍不够专属

赛车源校验了恰好10个1～10互异号码；非赛车缺少按game_id定义的球数、号码范围、重复/区域限制。台湾宾果历史时间按抓取时刻和行号倒推，不能当成已经核实的源端开奖时间。

依据：`backend/services/lottery_sources.go:365`、`:511`。

### 当前尚未确认的原版规则

1. 原版站点身份及各彩种规则页；当前只能用既有赛车截图确认部分行为。
2. PC三种是否采用相同号码结构、精确和值、组合大小单双、极大极小、特殊和值及退款规则。
3. SSC前三/中三/后三、和局、龙虎及各形态范围。
4. 五个六合彩各自的特别号、正码、波色、生肖、尾数、连码等实际开放项和特殊号处理。
5. 宾果七种的原始数据源、排序方式、变换公式和同期开奖样本。
6. 各玩法赔率、每个具体和值是否独立赔率、单注/单期限额及组合指令语法。

旧文档`docs/lottery-games-checklist.md`更新于8月22日，仍将部分现已接168源的彩种写作“本地模拟”；本报告以本轮实际代码及只读数据库快照为准，没有覆盖旧文档。

## 5. 已核对一致的部分与验证边界

赛车已有证据能确认：

- `#`分隔投注组，不自行把后组改为下一名。
- 每个展开投注项分别按末尾金额计费，不平分整组金额。
- `489/0178/48`总576；`5/045/343`总1029；`68/单大/811`总3244。
- 冠军、亚军混合大小单双和号码的12项例子总240。
- 0作为赛车号码表示10；各名次独立选号不应串选；龙虎按镜像名次比较。

验证方式：

- 本地业务库只读统计30彩种、九项赔率、近期开奖结构；没有触发会补写配置的业务查询服务。
- 后端赛车/助手/校验/结算/BingoTransforms/InferPlay现有定向纯测试通过。
- 会员前端完整现有测试：**61个文件、530项通过**。
- 内存探针核对长指令、非赛车结果展示及平台五球公式；没有真实下注、派彩或历史修改。

现有测试通过不代表以上错误不存在：部分测试只覆盖已实现的赛车路径，未覆盖跨彩种契约或原版规则。上述原版缺失项也不可能靠本地回归证明一致。

## 6. 首轮建议处理顺序（修复进度以第0节为准）

1. 先确认并处理F1/F2/L1/L2这类会影响注单含义或中奖结果的问题；是否临时停用受影响玩法需管理员明确决定。
2. 将每彩种的号码结构、玩法清单、合法位置、大小单双阈值、和局与特别号规则独立建模，前后端和结算共享契约；不要继续以名称或球数粗略推断。
3. 明确实际原版，再补PC/SSC/六合彩专属玩法、宾果转换、赔率与详细选号界面。
4. 修R1～R5和结果显示，建立逐彩种输入→注单展开→金额→开奖→结算的回归样本。
5. 如需评估旧单影响，另做只读对账，再决定处理方式；不要重写历史结果、伪造开奖记录或直接删除账本。
