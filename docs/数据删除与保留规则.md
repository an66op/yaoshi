# 数据删除与保留规则

本系统不使用“一键清空数据库”。所有数据按用途分为四类，并且平台管理员只能通过“数据维护”先预览、再确认执行。

## 删除入口审计矩阵

| 分类 | 数据 | 允许的处理 | 代码入口 |
| --- | --- | --- | --- |
| 账务与流水 | 余额流水、回水、返佣、分账、红包与领取记录 | 追加更正或冲正；机器人测试流水可验证冷归档 | 无普通 `Delete`；仅 `data_lifecycle.go` 归档流程 |
| 注单与开奖 | 真人注单、期号、开奖结果、结算状态 | 撤单改状态并退分；错误进对账；机器人已结算注单可验证冷归档 | 无普通 `Delete`；归档前校验原行哈希 |
| 申请 | 入房、上下分、娱乐上下分 | 状态流转，已审核不可删除 | 无 `Delete`，数据库拒绝硬删 |
| 聊天与通知 | 真人聊天、客服、会员通知、后台通知 | 按保留策略软删除，可按任务恢复 | `chat_messages` / `notifications` |
| 机器人聊天 | 独立机器人账号发送的普通文本 | 按房间和日期单独软删除，真人消息与红包不进候选 | `robot_chat_messages`，默认关闭 |
| 可恢复配置 | 用户、活动、收款渠道、会员收款方式、前台彩票分类 | GORM 软删除或停用 | 模型均含 `gorm.DeletedAt` |
| 可重建配置 | 平台赔率限额、用户/房间赔率覆盖、机器人彩种绑定 | 在事务内删除旧值并立即重建；历史注单使用下注快照 | 受审计允许的有限 `Delete` 清单 |
| 审计日志 | 管理操作日志 | 先写入不可编辑归档，再移出热表 | `data_lifecycle.go` 专用流程 |
| 短暂垃圾 | 失败的未接受投注请求占位、上传失败的未发布临时文件 | 只在未产生业务和账务前物理删除 | `assistant_bet.go` / 上传失败回滚 |

除上表列明的有限入口外，代码测试会拒绝新增 GORM `Delete`、`Unscoped().Delete`、原生 `DELETE FROM` 或 `TRUNCATE`。数据库还会拒绝业务表的普通物理 `DELETE`；注单、余额流水和热审计表即使需要归档，也只有在数据生命周期事务设置一次性、事务级许可后才能移动，连接归还连接池时许可自动失效。软删除是 `UPDATE deleted_at`，不会触发该限制。

## 永久账务凭证

以下数据不能直接删除：会员、入房及上下分申请、真人注单、余额流水、开奖结果、结算记录、红包金额与领取流水、回水、返佣和渠道分账。

- 账号停用使用状态或软删除，历史业务仍保留原工作区归属。
- 注单和余额流水只能冲正或追加更正流水，不能覆盖原记录。
- 待开奖、异常待处理、工作区不明的数据永远不会进入自动清理。

## 可恢复内容

聊天消息、会员通知和后台通知按房间设置保留天数。到期后执行软删除，普通查询不再展示；每次操作保存任务编号、操作人、范围、数量和时间，可按原任务恢复。机器人普通文本可使用独立策略，通过 `workspace_robot_profiles` 与消息的 `workspace_id + user_id` 双重匹配，不会使用昵称猜测身份。

红包消息隐藏时只隐藏聊天卡片，不删除红包、领取记录和余额流水。

## 冷归档数据

机器人测试注单只有同时满足“已结算、对账正常、属于明确机器人账号、超过保留期”才可进入冷归档；归档前保存完整原行并校验哈希，成功后才从热表移出。真人、待开奖和异常数据受到硬保护。平台可查看归档明细并按任务整体恢复。

审计日志只允许“先归档后移出热表”，归档记录不可编辑。

## 可停用配置

房间、租户、代理、彩种、机器人、收款渠道和活动优先使用“停用”。用户、活动、收款渠道、会员收款方式和前台彩票分类的删除是软删除，避免历史参与记录或审核资料失去来源。赔率等可重建的配置项可以在事务内替换，但下注时保存的赔率、回水和分成快照不得改变。

## 可物理删除数据

只有没有业务引用的草稿、上传失败的临时文件、未产生投注或扣分的短暂请求占位，以及已完成保留期且已验证归档的热表副本可以物理删除。会员收款资料改为软删除。所有批量操作必须有明确工作区，不处理 `workspace_id = 0` 的遗留数据。

## 运行顺序

1. 先完成 PostgreSQL 备份并校验。
2. 在“数据维护”设置保留策略。
3. 选择单一房间或明确选择全部房间并生成预览。
4. 核对候选数、受保护数和动作后确认执行。
5. 从任务记录查看结果；发现误操作时使用对应恢复功能。
