# 聊天保留与容量规划

更新时间：2026-08-31。本文基于本地代码核查；没有对当前业务库执行压测，也没有测得线上承载人数。

## 1. 本次优化与清理边界

聊天气泡属于展示记录，注单、余额流水、开奖与结算属于业务事实。应当分别保留：清理过期聊天不能级联删除注单、流水、红包领取记录或审计证据，也不能影响待结算数据。真人与机器人应遵循同样的业务证据保护原则。

前端只加载最近消息，可以减少接口响应和浏览器渲染，但不能阻止数据库持续增长。数据库还需要到期清理、小批处理和执行监控。软删除只是隐藏记录；若长期只软删除，原表仍保存这些行。

本次第一阶段分别限制前端展示与可安全清理的数据库内容：

| 项目 | 本次处理 |
| --- | --- |
| 开奖页前端缓存与最终时间线 | 上限 200 条，长期驻留也不无限累积；这是展示/内存上限，不是数据库全表上限 |
| 游戏聊天独立策略 `game_chat_messages` | 建议保留 7 天，默认关闭，既有数据不会因更新代码立即被删；在后台明确启用后才自动处理 |
| 可清理内容 | 普通游戏聊天，以及正常已结算旧期的 `settlement` / `scoreboard` 展示；保留最新开奖锚点 |
| 始终排除 | 带 `request_id` 的命令、`application` 回执、关联申请/红包的消息、正式注单、余额流水及其他业务证据 |
| 自动永久清理回收站 | 独立配置回收站天数；`0` 表示关闭。只启用保留策略不会自动授权永久删除 |
| 调度预算 | 北京时间每小时第 10 分钟运行；每批 1,000 条，每工作区每种删除模式最多 5 批，整轮限时 2 分钟；没有候选数据时不追加空任务记录 |

命令与回执目前同时参与重试防重和业务关联，不能为了减少聊天行数直接删除。它们仍可能长期增长；后续应先把防重凭证与关联证据从展示内容中拆分，再设计归档与展示内容删除。**本次不是“所有下注相关记录只保留 200 条/7 天”，也没有清空全部下注聊天。**

PostgreSQL 的普通 `DELETE` 产生的旧行版本也不会立即消失。正常运行的 autovacuum/VACUUM 会使无用版本占用的空间可供后续写入复用，通常不会立即把同等空间归还操作系统；因此清理后磁盘文件大小未马上下降，不等于清理失败。不要把需要排他锁且需要额外磁盘的 `VACUUM FULL` 放进日常自动清理。见 [PostgreSQL 官方维护说明](https://www.postgresql.org/docs/current/routine-vacuuming.html)。

本文容量部分不替代后台实际保留配置；启用和调整删除策略时，应先核对预览范围、批次、业务排除条件和恢复边界。永久删除后的内容不能再通过软删除恢复；注单与账务不在本次内容清理范围内。

## 2. 当前架构及已有测试的边界

- 前后台是 React 静态应用，生产由 Nginx 提供资源；业务服务为 Go/Gin，持久化使用 PostgreSQL，Redis 承担共享运行时、推送桥接及协调工作。
- 会员使用 WebSocket 接收实时消息。连接正常时，开奖页聊天、助手状态等不再按 10 秒定时补拉；断线才恢复相应补拉。推送事件仍可能触发额外 HTTP 读取，不能把 WebSocket 理解为完全没有接口请求。
- 彩种目录正常连接时基础刷新间隔约 30 秒，服务器时钟约 60 秒校准；临近封盘/开奖会更快刷新，某些阶段约 2 秒。目录与时钟刷新在页面隐藏后暂停。每秒变化的倒计时主要在浏览器本地计算，不代表每秒访问后端。
- 当前机器人下注由 `room_activity.go` 直接调用下注服务写入 `lottery_bets`；这条路径不会为每次机器人提交再插入下注聊天命令/回执。前端 `GameFeed` 从注单合成机器人动态展示。真人聊天下注每个输入请求则保存 1 条 `text` 命令和 1 条 `application` 回执，不是每个展开投注项各保存一套。
- 当前开奖图由客户端 Canvas 按开奖数据绘制，不是每期开奖都往数据库保存两张图片。Canvas 的内存/渲染负担与持久化消息行数应分别核算。
- 后端 PostgreSQL 连接池目前是每进程最多 100 个、最多空闲 10 个。增加后端实例前，必须核算所有实例的连接总预算；100 个数据库连接不等于只能有 100 名在线用户。连接被占满后请求可能等待，需观测 `DB.Stats`，不能简单无限加大。见 [Go 官方连接池说明](https://go.dev/doc/database/manage-connections)。
- Nginx 部署模板有每 IP 的 API 限流及 WebSocket 连接限制。同一个出口 IP 的多人、办公室或压测机可能先触发这些限制，不能把 429 或连接拒绝直接当作 CPU 容量上限。测试应覆盖真实共享出口场景，不能直接关闭安全限流。

代码核查入口：`backend/main.go`、`backend/config/database.go`、`backend/ws/`、`backend/services/room_activity.go`、`backend/services/member_stats.go`、`backend/services/data_lifecycle.go`、`backend/services/game_chat_lifecycle_scheduler.go`、`new/src/hooks/useLotteryGames.ts`、`new/src/utils/gameCatalogRefresh.ts`、`new/src/utils/gameTimelineBudget.ts`、`new/src/utils/drawResultCardCanvas.ts`、`new/src/pages/GameRoom.tsx`、`deploy/nginx/`。

现有 `tests/system/load-smoke.mjs` 默认只执行 500 次读取、20 次普通聊天写入、并发上限 20，以及 10 次建立后立即关闭的 WebSocket 连接。它不下注、不改资金，也不是持续在线测试。脚本默认错误率门槛 1%、P95 1500ms，适合发现明显回归，不能据此宣称已支持几百或几千人同时在线。已有系统测试说明见 [生产验收测试](生产验收测试.md)。

## 3. 先区分三个“人数”

| 指标 | 含义 | 主要影响 |
| --- | --- | --- |
| 注册会员数 | 数据库里存在多少账号 | 账号、索引与历史存储；不是持续请求量 |
| 同时在线会话数 N | 此刻保持连接/访问页面的浏览器会话 | WebSocket、内存、推送广播、校准/补拉；同一人多开也要计数 |
| 活跃提交人数 A | 此刻真实持续提交业务请求的用户 | 事务、写入、锁竞争、消息、结算；通常是在线人数的一部分 |

另外记录活跃房间数、每房机器人频率、每次请求展开的具体投注项数 K。一次输入可能包含多个名次和号码，即使只显示一条回单，也可能落入 K 条业务注单；减少聊天记录不会消除这些正确的业务写入。

## 4. 用请求量与消息量估算

### 在线读取

单个接口的基础轮询 RPS = `在线且会拉取该接口的会话数 ÷ 间隔秒数`。

多个接口要分别计算再相加，并加上首次进房、切换页面、WebSocket 触发的补读和失败重试。比如 1,000 个可见在线会话，仅按一个 30 秒目录接口和一个 60 秒时钟接口计算，约为 `1000/30 + 1000/60 = 50 RPS`；这不是整站总流量。若其中一个接口在边界切到 2 秒，单该接口就可能达到 500 RPS，且请求容易集中在同一秒。

### 业务提交与聊天写入

设每个活跃用户平均每 T 秒提交一次，每分钟机器人请求数为 R，真人与机器人每次提交分别新增 M_user、M_robot 条聊天记录：

```text
用户提交请求/秒 = A / T
机器人提交请求/秒 = R / 60
业务明细写入/秒 ≈ (A / T + R / 60) × 平均投注项 K
聊天新增行/秒 ≈ (A / T) × M_user + (R / 60) × M_robot + 其他普通聊天/结算展示行数
可清理类别保留行数 ≈ 该类日均新增行数 × 该类保留天数
受保护命令/回执保留行数 ≈ 历史累计新增量，不能套用本次7天清理公式
```

当前真人聊天下注路径 `M_user = 2`，当前机器人自动下注路径 `M_robot = 0`；未来增加机器人普通聊天时，要按对应新路径另行统计。一次批量输入只保存命令与汇总回单，不为每个展开投注项复制整套聊天气泡。接口重试和推送重连也不应再次插入相同回单。

算术示例，不代表实测容量：100 名真人每人 30 秒提交一次，100 个机器人房间每房 60 秒提交一次，忽略机器人每日上限时共约 5 次业务提交/秒。按当前路径，直接产生的命令/回执聊天约为 `100/30×2 + 100/60×0 = 6.67 行/秒`，不是 10 行/秒；只有该真人提交负载全天持续才会达到 576,000 行/天。其他聊天及结算展示还需另计。实际应按每日活跃小时积分，并计入机器人每日上限、睡眠时段和停用情况，不能直接把峰值乘 24 小时作为日均。机器人的聊天新增为零，也不意味着注单、账务、结算和推送没有成本。

### 推送与磁盘

```text
推送投递次数/秒 = Σ(每房新事件/秒 × 该房在线订阅会话数)
推送带宽约值 = 投递次数/秒 × 平均事件字节数 × 8
聊天热存储约值 = 保留行数 × 实测每行平均空间(含索引/TOAST)
总磁盘预算 = 热表 + 业务历史 + 索引 + WAL + 备份 + 图片/上传 + 清理缓冲
```

同样 1,000 人分散在 100 个房间，与 1,000 人集中一个高频房间，推送压力不同。图片下载、TLS 开销、初次静态资源和数据库复制流量需另外统计。存储每行大小用实际样本测量，不按固定“1 KB/条”作采购依据。

## 5. 服务器选型：仅是压测起点

以下不是已验证承载量或在线人数承诺。假设使用稳定 CPU、SSD/NVMe、合理数据库索引与连接池，静态图片资源另行计量；各供应商 vCPU、磁盘 IOPS 和网络差异很大。同规格不能保证同结果。

| 初始候选规格 | 定位 | 建议先验证的同时在线会话档位，非承载结论 |
| --- | --- | --- |
| 4 vCPU / 8 GB | 本地之外的小规模测试、单机全栈起步 | 50 → 100 → 300 |
| 8 vCPU / 16 GB | 较充足的单机试运行资源预算 | 100 → 300 → 1,000 |
| 16 vCPU / 32 GB | 更高负载的测试候选；同时比较数据库独立部署 | 300 → 1,000 → 3,000 |

每档都先采用“90%在线浏览、10%每30秒提交一次”的轻业务假设，再单独测更高活跃比例、多项提交、热门房间、断线恢复和同步结算峰值。若第一个档位已不达标，立即停止加压并诊断，不是必须测到表中上限。业务写入测试必须使用获准的隔离测试库与测试账号，不能直接在业务服务器上造真实注单。

当前阶段可以把 8 vCPU / 16 GB 作为预算与压测候选；如果现有测试机资源足够，先在现有机器取得基线，不必只因机器人账号多就换服务器。磁盘容量按上一节真实增长量、业务历史期限和备份策略决定；至少为清理、WAL、升级和恢复留余量，不只看当前数据库大小。

## 6. 正式容量验收条件

以下数值是本项目建议的验收目标，不是官方给出的通用性能保证，也不是当前系统已经达到的成绩。

| 项目 | 建议目标/门槛 |
| --- | --- |
| 常规业务读取 | 分接口 P95 ≤ 500ms，错误率 < 0.1% |
| 隔离环境业务提交 | P95 ≤ 800ms；重复请求不重复扣款，不丢记录；正确性错误为 0 |
| 实时推送 | 从服务端提交到客户端收到事件 P95 ≤ 1s；分别检查丢失、重复、重连补齐 |
| CPU | 稳态平均 < 70%，不能持续高于 85%；观察高峰后是否恢复 |
| 内存 | 至少保留约 25% 可用余量，无持续增长、OOM 或明显换页 |
| 数据库 | 无持续锁等待积压；连接占用预警 70%，不长期超过预算 80%；观察池等待时间、慢 SQL、WAL、检查点和 I/O 延迟 |
| 清理 | 过期积压可收敛，单批耗时可控；清理窗口的读写 P95 不明显恶化 |
| 磁盘/Redis | 磁盘建议在 70% 使用率预警；Redis 在 maxmemory 70% 预警，不能靠驱逐关键运行时键缓解 |
| 结算/后台任务 | 高峰过后队列能回落，不能每轮增长；测试跨多个开奖周期 |

P95 和错误率应按接口/场景分组，不能让大量快速 `/health` 请求稀释较慢的下注或聊天接口。k6 支持按指标定义失败门槛和中止条件，但测试目标值需要由项目自行定义，见 [k6 官方 Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)。PostgreSQL 可从 `pg_stat_activity`、`pg_stat_database`、`pg_stat_user_tables` 等观察活跃会话、事务、死元组和维护情况，见 [PostgreSQL 官方统计视图](https://www.postgresql.org/docs/current/monitoring-stats.html)。

建议每档先预热 5 分钟，再稳态运行至少 30 分钟；候选最终档位补 2 小时稳定性测试，并测一次清理、一次断线恢复与若干结算高峰。记录版本、机器规格、数据库数据量、缓存冷热、房间分布、请求配比及全部门槛，才可以给出“在这些条件下验证可承载 N 个在线会话”。正式运行仍应保留至少约 30% 余量，并随业务配比重新验证。

WebSocket 不仅消耗 Go 连接，也经过 Nginx。`worker_connections` 包括客户端和上游连接，不能直接等同在线人数；还要核对进程文件描述符限制，见 [Nginx 官方连接说明](https://nginx.org/en/docs/ngx_core_module.html#worker_connections)。当前 Redis 模板采用 `noeviction`，超过内存限制可能拒绝写入，所以必须在达到上限前告警，见 [Redis 官方内存策略说明](https://redis.io/docs/latest/develop/reference/eviction/)。

## 7. 实施顺序

1. 本次先限制开奖页前端缓存与时间线至 200 条；正式注单、流水和命令防重证据保持完整。
2. 本次新增独立、默认关闭的游戏聊天保留策略与可选永久清理；启用前确认预览，启用后关注可清理内容的积压、失败和数据库空间复用。
3. 统计真实每分钟提交、消息行、在线连接和推送投递，确认机器人是否在无人房继续产生负载。
4. 后续先拆分长期命令防重凭证和展示内容，再设计命令/回执归档；不能把本次清理当成它们的长期增长解决方案。
5. 在隔离环境补持续 WebSocket、多用户/多房间、重连及业务高峰测试。现有烟测不能替代这一步。
6. 根据瓶颈决定优化 SQL、调整推送/刷新合并、数据库独立部署或增加后端实例；不能只根据注册数或机器人账号数采购。
